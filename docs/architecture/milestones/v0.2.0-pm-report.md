## 2. dev 中發現、PM 未必看過的事

### 2.1 5 個 bug 是手測抓到的，而不是 BDD

M5 dev 中後段做完功能後我自己跑 chrome-devtools-mcp 手測，抓到 5 個 bug（已修）：

| Bug | 嚴重度 | 為何單元測試沒抓到 |
|---|---|---|
| Settings routing 3 keys silently dropped | P0（功能無感失效）| zod schema 預設 `.strip()` 把 schema 沒列的 key 丟掉；單元測試只測 schema 列的 key |
| CharacterEditor 儲存無錯誤回饋 | P1（使用者以為儲存成功）| 元件測試沒 mock fail response |
| Manual placeholder 讀回變成假內容 | P1（資料一致性）| 寫入/讀取分別有測，但 round-trip 沒測 |
| better-sqlite3 ABI mismatch | P0（執行時 crash）| 跨 Node 版本問題，CI 同版不會發生 |
| SSE write 對 closed stream throw | P1（log 噪音，沒掉資料）| race condition，要實際斷線才會發生 |

**已加 3 個 regression test 鎖死前 3 個**（commit `64cf1f5`）。

**給 PM 的訊號**：純單元測試 + 手測抓不到所有 case，BDD step def 補上後（M6 早期）有助於把上述 round-trip / fail-path 機械化。

### 2.2 native module ABI 升級（user 環境）

使用者實際機器上 Node 從 v18 升到 v26 後 better-sqlite3 / sharp 噴 `NODE_MODULE_VERSION 108 → 147`。已加 `postinstall: pnpm rebuild better-sqlite3 sharp`，未來新貢獻者 `pnpm install` 自動補。

### 2.3 status-updater 卡住（未完全解決）

採用 AI 章節後「狀態更新中…」會卡住的 root cause 是兩件事疊加：
1. statusUpdater routing 指向 `google:gemini-2.5-flash`，這個 endpoint 有時候 timeout / quota issue
2. job-event-bus 30s 內沒新 event 就 SSE timeout，client 沒收到 `failed` 事件→ phase 卡 running

**目前處理**：建議使用者把 statusUpdater 切到 LM Studio（地端）。
**真正修法（M6 候選）**：
- status-updater 加 90s timeout + 強制 emit `failed`
- StatusUpdateIndicator 加 60s client timeout + 重連
- job-event-bus SSE timeout 30s → 5min

要不要 M6 排這三項？決策見下方第 6 段。

## 6. 需要 PM 拍板的 3 件事

### Q1：M6 第一個 milestone 要不要分成兩塊？

兩個分法：

| 選項 | 內容 | Pros | Cons |
|---|---|---|---|
| **A. M6 = 「品質補強」** | M6-A BDD + M6-B 測試 + M6-C status-updater + M6-D 拋光 + M6-E user feedback | 還掉 M5 的技術債、品質曲線上升 | 無新功能、user 看不到差別 |
| **B. M6 = 「品質補強 + S1 全文搜尋」** | 上述 + S1（FTS5 全文搜尋） | 有 user-visible 功能 | scope 變大；FTS5 牽涉 ADR-0001 補強 |
| **C. M6 = 純品質（A）, M7 = S1** | A → 收尾 → 再開 S1 | scope 乾淨 | M6 對 user 沒亮點 |

**dev 推薦**：B（品質 + S1），因為 FTS5 與既有 cache-db 同層，技術上不衝；user 也會明顯感受到全文搜尋。但這要您拍板。

### Q2：M6-E（v0.2.0 user feedback collection）要不要正式開？

建議**正式開**一個 issue 收 release 後 1~2 週的 bug / feedback。M5 開發中發現的 5 個 bug 都是手測抓的，user 實際用 30 分鐘可能再噴 3~5 個。

### Q3：status-updater 卡住要不要當 P0 排 M6？

實際只有「status 自動更新」會卡，章節已採用、git 已 commit、資料安全。
但 UX 上看起來像「壞掉」，user 很容易誤判。

| 選項 | 行動 |
|---|---|
| **P0** | M6 第一週做完 |
| **P1** | M6 中段做 |
| **defer** | 等下次 user 抱怨再修 |

**dev 推薦**：P1（會在使用者抱怨之前修，但不擋 M6 開頭）。
